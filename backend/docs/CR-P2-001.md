# CR P2 001 Due date rule clarification

Status: PROPOSED, not approved. Raised during the 16 September 2026 source review. Requester: AI-assisted review for the team; no stakeholder approval claimed.

Original evidence: R3 and FR-009 describe a due date later than creation; AC-F09 rejects past due dates and requires future due dates. These statements disagree when an old request is assigned a due date between its creation and the current time.

Proposed wording: When staff assign or reschedule a request, the due time must be strictly later than the server's current time. Existing due times may naturally become overdue without invalidating the record. Store timestamps in UTC; display in the user's local timezone. Reporting dates use UTC boundaries, stated on the screen.

Business value: avoids newly assigned work appearing overdue immediately and gives a deterministic validation rule. Impact: FR-008/FR-009, AC-F08/AC-F09, R3, request-service futureDate validation, assignment/scheduling UI, tests T06/T19, RTM, ADR-P2-001 and P2-R06. No additional database column or external cost. Team effort estimate: one short review plus any policy/test adjustment; not a committed schedule.

Alternative: require only later than creation, which permits intentional retrospective scheduling. Team/lecturer must decide whether this is useful. Recommendation: accept the future-time rule for the pilot. Current candidate uses it, but must not be represented as approved until the team accepts it. If rejected, change code and acceptance tests together and preserve this proposal.

Approval outcome: PENDING. Approver/date/review link: not recorded.

## Approved team decision — 18 October 2026

Current status: APPROVED. This decision supersedes the proposal and pending
approval statements above, which are retained as historical context.

Edward Goosen, Albert Du Plooy and Amelia van der Walt explicitly agreed
in the PR #28 discussion: https://github.com/Amelia-VanDerWalt/CivicConnect/pull/28

When assigning or rescheduling a request, its due timestamp must be
strictly later than the server's current time. Existing requests may
naturally become overdue. UTC storage and local display remain unchanged.

This clarification resolves the FR-009/AC-F09 ambiguity. It removes no
scope and leaves the original 21-criterion denominator unchanged.
Existing implementation and tests already enforce this rule; no runtime
code change was required by this decision.
